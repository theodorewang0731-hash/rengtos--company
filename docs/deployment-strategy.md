# RegentOS 部署与模型接入策略

本文档对应 README 中的部署章节，重点回答三个问题：

1. 哪些能力优先本地部署
2. 哪些能力适合远程 API
3. 哪些能力必须进入远程内网 / 私有云

## 1. 三类模型来源

RegentOS 每个 Agent 最终都可以绑定三类模型来源：

- 远程 API 模型
- 本地蒸馏 / 量化 / 专项配置模型
- 本地完整大模型

这不是三选一，而是根据角色职责做部署编排。

## 2. 本地部署优先

最适合本地部署的是个人层 Agent：

- 个人通政司
- 个人内阁
- 个人司礼监
- 个人台谏院
- 个人锦衣卫

原因：

- 最贴近本地文件、本地代码、本地工具、本地执行风险
- 需要终端控制与低时延
- 需要访问个人上下文和本地状态

## 3. API 接入优先

最适合接远程大模型 API 的，是偏推理、归纳、起草和报告生成的能力：

- 票拟草案生成
- 需求澄清
- 回奏撰写
- 驳回理由生成
- 风险说明生成
- 修复建议生成
- 老板 / 董事会简报生成

这些能力不必直接持有终端控制权，但需要更强的语言推理与总结能力。

## 4. 远程内网 / 私有云部署优先

最适合远程内网部署的是部门层与公司层的公共治理能力：

- 部门通政司 / 内阁 / 司礼监 / 台谏院 / 锦衣卫
- 公司通政司 / 内阁 / 司礼监 / 台谏院 / 锦衣卫
- Case Registry
- Event Bus
- State Machine
- Permission Matrix
- Memorial Archive / Replay
- Dashboard / 文渊阁中枢
- 动态执行池
- 模型路由与权限服务

原因：

- 需要跨人、跨部门、跨层级治理
- 需要统一归档、统一审计、统一权限校验
- 需要把关键治理能力放进可控的企业基础设施

## 5. 一句话部署规则

- 本地部署：接触终端、接触个人上下文、拦截本地动作
- 远程内网服务：跨人、跨部门、跨层级的治理、归档与控制
- 远程 API：高质量推理、票拟、总结、驳回说明、修复建议

## 6. 当前 MVP 的实际状态

当前仓库只是 MVP，实际实现的是：

- 基于 FastAPI 的最小 API 控制面
- 内存版 Case Registry / Event Bus / State Machine
- 最小权限矩阵
- 最小修复受令链
- 时间线导出

尚未实现的部分包括：

- 多租户权限系统
- 企业身份接入
- 真实消息总线
- 持久化数据库
- Dashboard / 文渊阁中枢
- 真实分层调度与分布式执行池

所以当前仓库更适合被视为治理骨架，而不是最终生产形态。
